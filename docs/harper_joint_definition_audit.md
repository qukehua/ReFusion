# HARPER 官方节点定义核查

核查日期：2026-09-21。官方代码版本：`81b0ef1fd497cde7693fc9720ff35936ecb216e0`。
索引均从 **0** 开始。本文件区分官方明确写出的名称、根据连边的结构推断，以及官方没有解释的内容。

**作者已确认的项目约定**：作者在本次对话中将自己使用的 HARPER 数据中 21、22 号点定义为
相机相关点，并明确要求不参与计算。项目已据此固定使用原始 23 点数组的 0–20，删除 21/22。
这是作者对项目数据与输入协议的确认；下面的官方命名表保留原样，不将作者命名写成上游源码注释。

4. [官方 README 数据格式](https://github.com/intelligolabs/HARPER/blob/81b0ef1fd497cde7693fc9720ff35936ecb216e0/README.md)：
   human_joints_3d 为 21×3，spot_joints_3d 被写成 22×3。

## 21、22、23 点为何不能直接等同

目前三个官方材料的表述分别是：正文/项目页 21 点，README 数组说明 22 点，links.py 23 个索引。
links.py 对 0 点“额外添加中心”的注释可以提供一种 22→23 的解释线索，
但当前公开读取与显示代码没有补点逻辑，因此这只是可能的历史约定，不能据此认定实际 PKL 的序号偏移。

同样，保留 0–20、去掉 21/22 在数学上会得到 21 个点，但这不证明官方论文的 21 点实验就采用了这一子集。
公开仓库没有发布足以闭合这条对应关系的节点生成/导出定义，仓库中也没有示例 PKL 可直接核实。

## 对 ReFusion 论文和项目的影响

1. **项目选点已明确**：两份 HARPER YAML 的 `harper_spot_joint_indices` 均为 0–20。
   公共 `utils/harper_layout.py` 定义这一约定；私有加载器、多模态加载器和预处理共同使用它。
   21/22 在坐标归一化、增强、条件编码和评估预处理之前删除，不进入模型计算。
2. 论文可明确写为：“对本文使用的 23 点机器人表示，排除作者定义的两个相机相关点
   （从 0 开始的索引 21、22），保留索引 0–20 的 21 个点。”
   官方源码仍将两点注释为 wrist/hand；“相机相关点”的命名依据来自作者确认。
   原论文也提及夹爪上的 RGB-D 相机，因此不能进一步推导为 HARPER 平台没有机械臂/夹爪。
3. 输入必须符合原始 `[F,23,3]` 约定，拒绝将 21/22 点数组静默套用同一索引。
   模型条件维度为 20 个非根人体点 + 21 个 Spot 点，即 41×3；预测为 20×3 人体坐标。
   测试验证改变甚至污染被排除两点不会影响条件 DCT、目标 DCT及评估预处理结果。
   作者的映射确认不等于本次已核验实际 PKL 或重新训练了论文结果。
4. 官方 Y-up 已有明确代码证据。本地 HARPER 全场景旋转已从绕 Z 改为绕 Y，
   并用测试检查高度不变及距离保持。该加载器仍按作者要求保留为本地私有代码。

本核查没有下载完整数据集，也没有使用第三方推测替代缺失的官方节点定义。
